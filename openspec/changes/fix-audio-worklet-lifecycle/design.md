# Владение аудиоресурсами в transport

## Контекст

Мотивация приведена в `proposal.md`. Дизайн нужен, поскольку исправление затрагивает общий audio helper, оба transport и асинхронную инициализацию worker.

До исправления `createAudioPort()` возвращает только `MessagePort`, а ссылки на `AudioContext`, `AudioWorkletNode` и обработчики жестов остаются внутри helper. `exit()` transport не может освободить эти ресурсы. У `dosDirect()` также нет общего cleanup для неуспешной инициализации. Сообщение `ws-err` и событие `Worker.onerror` сами по себе не означают завершение backend.

## Цели и ограничения

Изменить только внутреннее владение ресурсами и добавить проверки. Публичный API, WASM-протокол, алгоритм worklet и его включение по умолчанию не меняются. Нельзя заменять native worklet на ScriptProcessor ради прохождения lifecycle-теста.

Рабочая область этого change ограничена emulators. Пользовательские изменения, `native/dosbox-x`, соседний js-dos и его `node_modules` не меняются. Переключение зависимости и удаление временного обхода в потребителе относятся к `add-jsdos-mcp`, а не к этому change.

## Решения

### Внутренний дескриптор аудио вместо одного порта

`createAudioPort()` возвращает `{ port, dispose } | undefined`. Helper владеет контекстом, узлом и обработчиками жестов. `dispose` удаляет обработчики, закрывает доступный порт, отключает узел и запускает `context.close()` с обработкой ошибки. Ссылки очищаются, чтобы повторный вызов был безопасен. Закрытие контекста остаётся асинхронной операцией Web Audio; тесты дожидаются `closed`, а не только вызова метода.

Тот же disposer вызывается при частично завершившемся создании аудио. Существующий `undefined` fallback и освобождение blob URL в `finally` сохраняются.

Альтернатива с новым публичным методом очистки отклонена: владелец transport уже существует, и потребитель не должен исправлять lifecycle SDK вручную.

### Transport отвечает за освобождение своего дескриптора

Direct transport хранит дескриптор, передаёт в `module.audioPort` только порт и вызывает disposer из своего `exit()`. Ошибки `instantiate` и `callMain` проходят через тот же `exit()` с сохранением исходной ошибки и удаления существующего `message` listener.

Worker transport хранит дескриптор, передаёт в worker только порт и очищает аудио при `exit()`. Обработчик `worker.onerror` только передаёт существующее сообщение `ws-err`, без очистки аудио, принудительного завершения worker или флага отказа запуска. Ошибка обработчика не обязательно останавливает worker, а `CommandInterface.exit()` должен получить `ws-exit` перед завершением transport. Сообщения `ws-err` в обоих backend также не запускают cleanup. Существующая повторная попытка `wc-install` без предварительно скомпилированного WASM-модуля сохраняется; cleanup выполняется через `catch`, если и эта попытка выбрасывает ошибку.

Альтернатива с cleanup только на нормальном `ci.exit()` отклонена: она не закрывает ресурсы при ошибках до получения CI.

### SDK содержит собственную регрессионную проверку

Патч добавляет `test/src/test-audio-lifecycle.ts` и регистрацию в `test/src/node-runner.ts`. Проверяются normal exit, повторный exit и ошибка запуска для direct/worker, ошибки загрузки worklet и создания узла. По уточнению пользователя тесты ошибок worker проверяют сохранение аудио во время создания и работы, а не его очистку. Сообщение `ws-err` в обоих backend сохраняет аудио и доходит до существующего обработчика сообщений. Подменённые browser globals восстанавливаются в `finally`.

Дополнительно браузерный suite SDK проверяет реальные `AudioContext`: сохранение работающего аудио после `ws-err`, последовательные запуски и остановки, закрытие старых контекстов, отсутствие второго активного контекста при remount. DOSBox и DOSBox-X проверяются с включённым native worklet в обоих transport; для worker также проверяется `Worker.onerror`. Тест с mock не заменяет эту проверку; счётчик экземпляров CI также недостаточен.

Предыдущие 76 Node-тестов и браузерные проверки двух backend прошли в изолированном прототипе внутри js-dos. Это исходные данные для переноса, а не основание отмечать задачи текущего change выполненными.

### Стандартная поставка SDK

Патч применяется к исходникам SDK однократно. Он не становится build/postinstall hook, runtime-подстановкой или постоянной зависимостью от соседнего checkout.

После проверок нужно выбрать свободную совместимую patch-версию после `8.5.2`, обновить обычные release metadata и собрать SDK через `yarn run gulp production`. Проверка npm-архива должна подтвердить, что в него вошли пересобранные wrapper, WASM, декларации и лицензия, а не старый `dist`. Стандартный пакет проверяется в изолированном потребителе без замены файлов зависимости и без `JSDOS_TEST_EMULATORS_JS`.

Публикация npm и создание публичного релиза не разрешены одной лишь командой apply: нужны отдельное подтверждение пользователя и учётные данные. При отсутствии разрешения или доступа задача опубликованной поставки остаётся открытой. После публикации фиксируются версия, исходный commit и npm integrity; js-dos сможет самостоятельно закрепить эту версию в своём change.

## Риски и проверки

- Ошибка worker во время `addModule()` не доказывает завершение backend → отдельный тест сохранения позднего контекста и его очистки при последующем `exit()`.
- Успешный Node mock не доказывает освобождение browser audio thread → браузерная проверка реальных контекстов и native worklet.
- Текущая ветка SDK отличается от базы патча → проверить checksum, применимость и diff; не перезаписывать сторонние изменения.
- Старый `dist` способен скрыть отсутствие исправления в пакете → production-сборка и проверка установленного npm-архива, а не одного JS override.
- Публикация может быть недоступна → явно сохранить блокер и не объявлять потребителя разблокированным.

## Порядок выпуска и откат

Сначала перенести изменение и тесты, затем выполнить lint, TypeScript, обязательный `yarn test:node:build` и браузерные lifecycle-проверки. После этого собрать и проверить npm-архив, а публикацию выполнить только при отдельном разрешении.

При неуспешной проверке пакет не публиковать. После публикации откат потребителя к предыдущей версии выполняется отдельно и возвращает известную утечку; нельзя скрывать регрессию отключением native worklet. Этот change не объявляет `add-jsdos-mcp` завершённым: у него остаются собственные проверки и внешние блокеры.
